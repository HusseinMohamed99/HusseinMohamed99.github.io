Operating Modes and Technical Data Processing

2.1 Guest Mode (Unauthenticated)

Qisma is engineered to be fully functional without registering an account or providing an email address:

  • Local Financial Ledger Storage: The application generates client-side UUIDv7 identifiers for local identities, groups, members, expenses, itemized bill items, and settlements. These records are stored exclusively in an unencrypted SQLite database (splitly.sqlite) inside the operating system's private application sandbox on your physical device. No financial records, expense amounts, splits, settlements, group names, or member names are uploaded or synchronized to any remote server or cloud service.
  • Platform Infrastructure SDK Activity: While financial ledger bookkeeping remains strictly on-device, the application incorporates native platform SDKs (Firebase Core, Firebase Installations, Firebase App Check, and Firebase Crashlytics) that initialize at startup in staging and production builds. In staging and production builds, these SDKs transmit low-level network packets for anti-abuse verification (App Check device attestation tokens via Google Play Integrity on Android or Apple App Attest on iOS) and app stability monitoring (Firebase Installation ID and sanitized crash telemetry if an unhandled crash occurs). In development builds, remote diagnostic collection is programmatically disabled.

2.2 Authenticated Mode (Signed-In with Cloud Synchronization)

If you choose to create an account or sign in to synchronize groups:

  • Authentication Credentials: Firebase Authentication processes your email address and password (for email/password accounts) or Google OAuth tokens (for Google Sign-In). Passwords and OAuth tokens are handled exclusively in-memory and by provider SDKs; they are never stored in the application's local database.
  • Explicit Cloud Synchronization: Eligible signed-in users may explicitly initiate cloud synchronization for eligible groups. When explicitly triggered by you:
    • Group metadata, member lists, accepted expense descriptions, monetary amounts (as integer minor units), split allocations, and settlement records are transmitted over Firebase SDK TLS (TLS 1.2/1.3) to Google Cloud Firestore and Cloud Functions.
    • Itemized Bill Line Items Exception: Detailed bill line items, individual item prices, quantities, and per-item assignments remain 100% local on the device (per architectural policy D-059). Only the resulting net split totals are synchronized to the cloud.
  • No Background Synchronization: The application implements zero background sync workers, zero periodic timers, and zero background lifecycle upload hooks. Cloud synchronization executes strictly upon explicit user interaction in the foreground.

Optical Character Recognition (OCR) and Receipt Photos

When you use the receipt scanner to extract line items:

  • On-Device Machine Learning: Receipt OCR executes entirely on your device using native platform frameworks:
    • Android: Uses Google ML Kit's bundled on-device Latin model. Receipts with Arabic text require manual verification and entry in the review screen.
    • iOS: Uses Apple's Vision framework (VNRecognizeTextRequest), supporting Latin script and Arabic script on iOS 16+.
  • Image Lifecycle & Safe Cleanup:
    • Photographs captured via camera or selected from the photo picker are scaled and cached in the operating system's temporary directory cache.
    • Receipt images and extracted raw text never leave the device and are never uploaded to any server or cloud storage.
    • Temporary intermediate scaled image files are actively and deterministically deleted immediately upon OCR completion (or failure/cancellation) via TemporaryReceiptImageCleaner inside a try ... finally block.
    • Original photos located in device galleries (/DCIM/, /Pictures/, or Photos) are strictly protected and never modified or deleted.

Diagnostics, Telemetry, and Third-Party Processors

  • Advertising: Qisma contains no advertising SDKs. Advertising ID permissions (AD_ID, ACCESS_ADSERVICES_*) are explicitly stripped from the Android manifest.
  • Analytics: No client analytics SDK (such as Google Analytics for Firebase, Mixpanel, or AppsFlyer) is installed. Observability event logging is hardcoded to a no-operation sink.
  • Crash Reporting (Firebase Crashlytics):
    • Active only in staging and production builds; disabled in development.
    • Collects native stack traces, device model, operating system version, free storage/memory, and a pseudonymous Crashlytics Installation ID.
    • setUserIdentifier is never called; crash reports are unlinked from user accounts.
    • Application error payloads are sanitized: error messages are replaced with the runtime exception type name only (SanitizedReportedError), and contextual metadata is strictly restricted to an allow-list of 15 technical keys.
    • Google documents data retention for Crashlytics closed issues as 90 days.
    • Regulatory Disclosure Note: While the application code never links user accounts to crash reports, because the Firebase Installation ID (FID) coexists in the app sandbox, the final App Store Nutrition Label declaration (Option A: "Not Linked to You" vs Option B: "Linked to You") remains an open legal decision (LEG-05) pending final owner sign-off.

Storage Security and Platform Backup Controls

  • Local Sandbox: Financial records reside in getApplicationSupportDirectory() + '/splitly.sqlite'.
  • Android Backup Defense:
    • Declares android:allowBackup="false".
    • Configures android:dataExtractionRules="@xml/data_extraction_rules", excluding all app data from cloud backups and device-to-device transfers on Android 12+ (API 31+).
    • Configures android:fullBackupContent="@xml/backup_rules", excluding all backup domains on Android 11 and earlier.
  • iOS Data Protection & Backup Exclusion: During application launch, AppDelegate.swift enforces:
    • FileProtectionType.completeUntilFirstUserAuthentication on the application support directory and contained database files.
    • URLResourceValues.isExcludedFromBackup = true on the directory and database files, preventing inclusion in iTunes or iCloud backups.
  • Residual Risk: SQLite database files are not encrypted at rest with SQLCipher; security relies on the host device's operating system sandbox and hardware encryption. Rooted or jailbroken devices compromise this security boundary.

Account Deletion and Data Retention

Signed-in users can permanently delete their account at any time via Settings > Account > Delete account. Deletion requires recent re-authentication using your original authentication provider (Email/Password or Google Sign-In; Apple Sign-In is unsupported in version 1.0.2).

6.1 What is Deleted Immediately:

  1. The Firebase Authentication identity record (users/{uid}) is permanently erased from Firebase Auth servers.
  2. All cloud access permissions in groups/{groupId}/access/{accountId} and accounts/{accountId}/groupAccess/{groupId} are marked status: "revoked".
  3. Local account identity records in SQLite are marked status: "deleted", and the user is signed out to Guest Mode.

6.2 What is Intentionally Retained:

  1. Shared Financial History: Accepted historical expenses, split shares, settlements, and member display names in shared groups remain in Cloud Firestore and in the local databases of other group members.
    Accounting Integrity Rationale: In shared group ledgers, participant balances, running debts, and settlement obligations depend directly on the collective transaction history. Unilaterally erasing past transactions upon one member's account deletion would distort running balances and deprive surviving group members of their verifiable financial ledger and settlement records.
  2. Security Tombstones: Server-side records accounts/{accountId} and authPrincipals/{uid} are retained with status: "deletionPrepared" to prevent identity resurrection, replay attacks, or synchronization hijacking. These tombstones contain no profile names, emails, or phone numbers. A proposed 365-day tombstone retention period has received preliminary approval, but remains subject to final owner implementation review; no automated TTL or deletion policy is currently active in production.
  3. Retention Window Breakdown:
    • Active Data: Stored while account and shared groups remain open.
    • Shared Ledger History: Preserved in Cloud Firestore for the active lifecycle of the shared group.
    • Security Tombstones: Retained server-side without PII (preliminary 365-day schedule modeled; production automated TTL held disabled).
    • Diagnostics (Crashlytics): 90 days retention per Google standard policy.
    • Cloud Logging: 30 days retention in GCP _Default bucket; 400 days in locked _Required bucket.

6.3 Sole-Owner Guard:

A user who is the sole owner of an active group cannot delete their account until ownership is transferred to another active member via transferGroupOwnership or the group is deleted.

حذف الحساب والاحتفاظ بالبيانات

يمكن للمستخدم المسجل حذف حسابه في أي وقت عبر الإعدادات > الحساب > حذف الحساب. ويتطلب الحذف مصادقة حديثة باستخدام وسيلة الدخول الأصلية (البريد وكلمة المرور أو حساب Google؛ تسجيل الدخول بحساب Apple غير مدعوم في الإصدار ١.٠.٢).

٦.١ ما يُحذف فورًا:

  1. يُحذف سجل هوية المستخدم نهائيًا من خوادم Firebase Authentication.
  2. تُلغى كافة صلاحيات الوصول السحابية في المجموعات المتزامنة (status: "revoked").
  3. يُحدد الحساب المحلي في قاعدة بيانات SQLite كحساب محذوف (status: "deleted") ويتم تسجيل الخروج إلى وضع الضيف.

٦.٢ ما يُحتفظ به عمدًا:

  1. السجل المالي المشترك: تبقى المصروفات السابقة المعتمدة وحصص التقسيم والتسويات وأسماء الأعضاء في مجموعات المشاركة محفوظة في خوادم Firestore السحابية وقواعد بيانات الأعضاء الآخرين.
    سبب النزاهة المحاسبية: في الدفاتر المالية للمجموعات المشتركة، ترتبط أرصدة الأعضاء والتزامات التسوية والديون الجارية ارتباطًا مباشرًا بالسجل التاريخي للمعاملات المعتمدة. ويؤدي الحذف الأحادي للمعاملات السابقة عند حذف حساب أحد الأعضاء إلى تشويه الأرصدة الجارية وحرمان بقية أعضاء المجموعة من سجلاتهم المالية وقسائم التسوية القابلة للتحقق.
  2. سجلات الأمان الإجرائية (Security Tombstones): تُحفظ سجلات تقنية في الخادم لتأكيد اكتمال الحذف (status: "deletionPrepared") لمنع إعادة استخدام الهوية أو هجمات إعادة الإرسال. ولا تحتوي هذه السجلات على أي أسماء أو بريد إلكتروني أو هواتف. وقد نالت خطة الاحتفاظ بها لمدة ٣٦٥ يومًا موافقة مبدئية، لكنها تظل خاضعة للاعتماد التنفيذي النهائي من المالك؛ ولا توجد أي سياسة حذف تلقائي أو TTL مفعلة حاليًا في الإنتاج.
  3. تفصيل مدد ومدى الاحتفاظ:
    • البيانات النشطة: تُحفظ طالما كان الحساب والمجموعات المشتركة نشطة.
    • سجل الدفتر المشترك: يُحفظ في Cloud Firestore طوال دورة حياة المجموعة المشتركة.
    • سجلات الأمان التقنية: تُحفظ في الخادم دون بيانات شخصية (موافقة مبدئية على ٣٦٥ يومًا؛ سياسات الحذف التلقائي السحابية معطلة).
    • تقارير التشخيص: ٩٠ يومًا وفق سياسة Crashlytics القياسية لدى Google.
    • سجلات السحابة (Cloud Logging): ٣٠ يومًا في حاوية _Default و ٤٠٠ يومًا في حاوية _Required المغلقة.

٦.٣ قيد المالك الوحيد:

لا يمكن للمستخدم الذي يمثل المالك الوحيد لمجموعة نشطة حذف حسابه قبل نقل ملكية المجموعة إلى عضو آخر عبر وظيفة نقل الملكية أو حذف المجموعة.

القرارات القانونية والتشغيلية المعلقة

تتطلب العناصر التالية اعتمادًا صريحًا من الإدارة القانونية والمالكة للتطبيق قبل النشر:

  • [يلزم تحديد الكيان القانوني]: الاسم التجاري للشركة والولاية القضائية.
  • [يلزم تحديد المقر المسجل]: العنوان الجغرافي المسجل.
  • [يلزم تحديد القانون الواجب التطبيق والاختصاص]: النظام القضائي الحاكم.
  • [يلزم تحديد مدد الاحتفاظ]: تحديد المدد القانونية للاحتفاظ بسجلات الخادم التقنية والنسخ الاحتياطية.
  • [يلزم تحديد حقوق تصدير البيانات]: تحديد إجراءات تصدير بيانات المستخدم (وفقًا للمادة ٢٠ من GDPR).
